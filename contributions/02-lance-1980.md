## Contribution Summary

This contribution investigates Lance issue #1980: adding an `n_jobs`-style parallelism
parameter to `lance.write_dataset` so users can write large in-memory tables faster.

The reporter observed that a single `write_dataset` call uses `< 10%` CPU and `~20%`

## Problem Summary

`lance.write_dataset` currently processes its input as a single stream and writes one
file at a time, so a single call cannot saturate available CPU or network when the
source is a large fully in-memory table. The reporter measured meaningful throughput
gains only by manually running multiple writes across threads, which is awkward and
undocumented. The requested change is a first-class `n_jobs`-style parameter that lets
`write_dataset` fan a large in-memory table out into parallel fragment writes and then
commit them as one dataset. The core design question is where that parallelism should
live (Python orchestration vs. the Rust `WriteParams` path) and how to keep fragment,
commit, and error semantics correct.

## Reproduction

The benchmark script is kept **outside** the repository at `/tmp/lance_issue_1980_repro.py`.
It is self-contained and uses only existing dependencies (`pyarrow`, `numpy`, `lance`,
and the standard-library `concurrent.futures.ThreadPoolExecutor`) — no new `joblib`
dependency.

### How to run (numbered, executable without prior context)

1. Ensure the Lance Python environment is built once:
   ```bash
   cd /Users/adibaakter/dev/lance/python && uv sync
   ```
2. Raise the macOS open-file limit (precaution) and run the script through the project
   environment:
   ```bash
   ulimit -n 2048
   uv run --project /Users/adibaakter/dev/lance/python python /tmp/lance_issue_1980_repro.py
   ```
3. The script generates in-memory PyArrow tables, runs a warm-up plus 3 measured
   repetitions per case, prints median elapsed time, throughput, fragment counts, and a
   correctness verdict, then deletes all temporary datasets.

The script measures two scenarios:

- **Scenario A (original-reporter reproduction).** Several independent in-memory tables
  are written to **separate** dataset URIs, sequentially vs. concurrently via a
  `ThreadPoolExecutor`. This mirrors what the reporter actually did (many tables, each in
  its own thread).
- **Scenario B (maintainer-aligned implementation target).** **One** in-memory table is
  split into `n_jobs` parts, each part written with `lance.fragment.write_fragments` in a
  thread, then all fragments committed to a **single** dataset via a `LanceOperation`.
  This is the exact shape of `wjones127`'s accepted `write_lance_parallel` reference and
  the most likely internal behavior of an in-call `write_dataset(..., n_jobs=)` parameter.

Each output dataset is verified: row count, schema (column names), full content equality
on the `id` and `val` columns (after sorting by `id`), and a representative checksum on
the `vec` column, plus the resulting fragment count.

### Expected behavior

`lance.write_dataset` should let a caller opt into parallelism for a large in-memory
table (e.g. `n_jobs=4`) and use more of the available CPU/network, reducing wall-clock
write time while producing a dataset that is byte-for-byte equivalent in row count,
schema, and content to a sequential write.

### Actual behavior (current API)

`lance.write_dataset` exposes **no** `n_jobs` / `num_workers` / `num_threads` /
`write_parallelism` parameter. The only way to parallelize today is to orchestrate it
externally (multiple `write_dataset` calls, or manual `write_fragments` + commit), which
is undocumented on this API and easy to get wrong (fragment collection, commit mode,
error handling).

## Root-Cause Hypothesis

This is an enhancement, not a defect, so the "root cause" is a design limitation:
`lance.write_dataset` delegates to a Rust write path whose `WriteParams` has **no**
notion of intra-write parallelism, and the writer consumes its input as one sequential
`RecordBatch` stream writing one file at a time (confirmed by the maintainer and by the
absence of any worker-count field in `WriteParams`). Consequently a single large
in-memory input cannot be fanned out across cores or connections within one call, so CPU
and network stay under-utilized. The fix is to add an opt-in worker count that partitions
an in-memory input and writes fragments concurrently, then commits them as one dataset.

### Strongest "Match" in the repository

`CompactionOptions.num_threads: Option<usize>` in `rust/lance/src/dataset/optimize.rs`
(around line 189) is a near-exact precedent for the parameter this issue wants:

- Its doc comment says *"The number of threads to use ... Defaults to the number of
  compute-intensive CPUs."*
- It is consumed as
  `...num_threads.unwrap_or_else(get_num_compute_intensive_cpus)` inside a
  `buffer_unordered(...)` concurrency limit (around line 805) — i.e. `None` means "use
  the sensible default", a concrete value caps parallelism.
- The default helper is `get_num_compute_intensive_cpus()` in
  `rust/lance-core/src/utils/tokio.rs` (around line 19), which caches `num_cpus::get()`,
  honors the `LANCE_CPU_THREADS` env override, and reserves I/O cores.

This gives a project-blessed answer to several design questions: an `Option<usize>` where
`None` preserves current behavior via a CPU-based default, and a reusable helper instead
of hand-rolled concurrency. On the Python side, `batch_readahead` / `fragment_readahead`
(`Optional[int] = None`, wired via `setopt` in `dataset.py`) show the matching Pythonic
convention for optional concurrency knobs.

## UMPIRE Implementation Plan

### Understand

- **User problem:** a single `write_dataset` call on a large in-memory table under-uses
  CPU/network; parallelism is only achievable via awkward external orchestration.
- **Reproduction:** `/tmp/lance_issue_1980_repro.py` (above); concurrent writes are
  1.58×–2.35× faster locally with identical correctness.
- **Expected vs. actual:** expected an opt-in `n_jobs`; actual API has none.
- **Current call path:** `lance.write_dataset` (Python) → `python/src/dataset.rs` (PyO3)
  → Rust write path driven by `WriteParams` (single stream, one file at a time).

### Match

- **Comparable implementation:** `CompactionOptions.num_threads: Option<usize>` in
  `optimize.rs`, defaulted via `get_num_compute_intensive_cpus()` and used as a
  `buffer_unordered` limit — the pattern to imitate.
- **Comparable validation/testing pattern:** `python/python/tests/test_dataset.py` write
  tests; project standard is `@pytest.mark.parametrize` for input-only variations and
  `assert`-based correctness (no timing assertions).
- **Relevant history/context:** the accepted maintainer reference (`write_lance_parallel`)
  splits one table into parts, writes fragments per part in threads, and commits with
  `LanceOperation.Append`/`Overwrite`.

### Plan

- **Preferred (minimal, maintainer-aligned):** add `n_jobs: Optional[int] = None` to the
  Python `write_dataset`. When set `> 1` **and** the input is a fully materialized
  in-memory table (`pa.Table` / equivalent), partition into `n_jobs` slices, call
  `write_fragments` per slice concurrently, then commit all fragments as one dataset
  (`Append` if it exists, else `Overwrite`) — i.e. productionize the maintainer's
  reference behind the public API. `None`/`1` → today's exact single-stream path.
- **Alternative (deeper):** thread a worker count into Rust `WriteParams` so the core
  writer fans out internally, reusing `get_num_compute_intensive_cpus()` for the default.
  More robust and shared across bindings, but larger and needs maintainer buy-in.
- **Files likely to change:** `python/python/lance/dataset.py` (param + validation +
  docstring), possibly `python/src/dataset.rs` and `rust/lance/src/dataset/write.rs` for
  the alternative; tests in `python/python/tests/test_dataset.py`.
- **Backward compatibility:** `n_jobs=None` (default) must be byte-for-byte identical to
  current behavior; no signature break.
- **Parameter semantics:** `None` and `1` → sequential (unchanged). `>= 2` → that many
  parallel fragment writers. Reject `0`, negatives, and non-integers with a descriptive
  error at the API boundary (per repo standard: never silently clamp). Avoid `-1` "all
  cores" magic unless maintainers want it, since it is inconsistent with the existing
  `num_threads`/`None`-default convention.
- **Error handling:** if any worker fails, surface the first error and do **not** commit a
  partial dataset (all-or-nothing commit).
- **Tests:** parametrized correctness tests (`n_jobs` ∈ {None, 1, 2, 4}) asserting equal
  row count/schema/content and expected fragment count; multi-fragment scenario;
  validation tests for `0`/negative/non-integer; NULL/empty-table edge cases.
- **Documentation:** docstring with the semantics above and a short example; note it
  applies to in-memory inputs.

### Review

- **Risks:** fragment/commit correctness under concurrency; transaction atomicity
  (partial failure must not commit); ordering across fragments; thread safety of the
  PyO3 boundary; input types that are streaming/lazy and cannot be safely partitioned;
  behavior differences on cloud object stores (the reporter's real target) vs. local SSD.
- **Questions for maintainers:** Python-level orchestration vs. Rust `WriteParams`? Should
  `n_jobs` silently no-op for non-in-memory/streaming inputs or raise? Preferred default
  semantics and whether to reuse `get_num_compute_intensive_cpus()`? Is `Append` vs.
  `Overwrite` selection acceptable, or should mode be explicit?
- **Why appropriately scoped:** the preferred plan reuses an accepted reference and an
  existing primitive (`write_fragments`), changes one public signature additively, and
  defers the deeper Rust change unless requested.

### Evaluate

- **Objective correctness criteria:** for every `n_jobs`, the resulting dataset equals the
  sequential result in row count, schema, and content; fragment count matches
  expectation; invalid `n_jobs` raises.
- **Targeted automated tests:** the parametrized `write_dataset` tests above in
  `python/python/tests/test_dataset.py`.
- **Broader regression:** `uv run pytest python/python/tests/test_dataset.py -k "write"`
  plus the existing suite.
- **Manual benchmark method:** the `/tmp` script (median of 3 reps after warm-up),
  ideally re-run against an object-store backend before claiming production benefit.
- **Explicit note:** timing/speedup assertions must **not** be placed in unit tests —
  they are environment-dependent and flaky; unit tests assert correctness only.

## Edge Cases to Cover

- `n_jobs=None` and `n_jobs=1`: identical to current behavior.
- `n_jobs=0`, negative, or non-integer: descriptive error.
- `n_jobs` greater than row count / tiny tables: must not crash or produce empty fragments.

### Implementation summary

Added an optional `n_jobs` argument to `lance.write_dataset`:

- `n_jobs=None` (default) and `n_jobs=1` preserve the existing sequential write path
  exactly — no behavior change for existing callers.
- `n_jobs >= 2` enables parallel writing for a materialized `pyarrow.Table` with
  `mode="overwrite"`:
  - the table is divided into contiguous, non-empty partitions;
  - partitions are written concurrently through `lance.fragment.write_fragments`
    (via `concurrent.futures.ThreadPoolExecutor`, a standard-library tool — **no new
    dependency**);
  - the resulting fragments are collected in **deterministic partition order**;
  - all fragments are committed in **one final `LanceOperation.Overwrite` transaction**.
- **Effective workers are capped at the number of non-empty partitions**, so a small
  table with a large `n_jobs` never spawns idle or empty workers.
- **A worker failure prevents the final commit** — the first worker error is re-raised
  before the commit, so no partial dataset version is produced. (Fragment files already
  written by completed workers may remain uncommitted in storage; this matches the
  documented behavior of the low-level `write_fragments` API and is noted in the
  docstring.)
- **Parallel `create` and `append` are explicitly rejected** (clear error), because the
  public fragment-commit path cannot safely reproduce their concurrency/transaction
  guarantees (see *Engineering challenge* below).
- **Unsupported input types and incompatible options raise clear errors** rather than
  silently degrading to a sequential write.

### Implementation decisions

- **Python-level orchestration** (the maintainer-endorsed `write_lance_parallel` shape),
  not a Rust `WriteParams` change — kept the first contribution small, additive, and
  reviewable. The deeper Rust-core option is recorded as future work.
- **`mode="overwrite"` only** for parallel writes. `LanceOperation.Overwrite`
  ("overwrite or create", no `read_version`) is the one commit shape whose semantics the
  Python fan-out can reproduce faithfully; `create` and `append` are rejected rather than
  weakened.
- **Kept the parameter name `n_jobs`** because that is the exact name requested in issue
  #1980. Lance's other worker-count knobs use names like `num_workers` /
  `*_concurrency`; the naming choice is flagged as a maintainer discussion point for the
  eventual PR rather than pre-emptively renamed.
- **Reject-don't-clamp** for invalid values, per the repo's error-handling standard
  (`bool`, non-integer, `0`, and negatives all raise with a descriptive message).

### Engineering challenge and resolution

The first draft attempted to support parallel `create`, `overwrite`, **and** `append`.
A code review found that Python-level fragment commits could **not** safely preserve:

- the **atomic create-only** guarantee the native writer enforces (it raises
  "dataset already exists"); nor
- **append's conflict-detection / retry** semantics (the native append path retries on a
  commit conflict; a blind `Overwrite(read_version=None)` can silently replace a
  concurrently-created dataset).

Rather than ship modes whose concurrency guarantees were quietly weakened, I deliberately
**narrowed the scope to parallel `overwrite`**, which is provably correct with the
existing public API. This also removed the fragile dataset-existence detection and
error-message parsing, shrinking the diff and making the contribution easier to review.
Parallel `create`/`append` are documented as **future work** that likely needs stronger
transaction primitives or a Rust-core implementation (which owns those semantics and
could be shared across all bindings).

### Edge cases covered by tests

- `n_jobs=None` and `n_jobs=1` (sequential compatibility across `create`/`overwrite`/`append`)
- parallel worker counts `2` and `4` (correctness: row count, schema, content)

- Boolean and non-integer values → `TypeError`

- empty table (no zero-worker executor; valid empty dataset)
- null-valued columns
- unsupported input types (e.g. `RecordBatchReader`, pandas) → clear error
- unsupported options (e.g. `commit_message`) → clear error
- explicit `schema=` with parallel mode → rejected (not silently ignored)
- unsupported parallel `create` and `append` modes → clear error
- worker failure before final commit → no dataset version created
- multiple fragments produced (asserted `> 1`, **without** guaranteeing an exact count)

### Known limitations (documented as future work)

- Parallel writes are limited to in-memory `pyarrow.Table` + `mode="overwrite"`.
- Parallel `create`/`append` are not supported (transaction-semantics reasons above).
- On worker failure, orphan fragment files may remain uncommitted in storage.
- Speedup evidence is local-SSD only (Phase II); object-store/production gains are
  expected but not proven here.

### Pull Request Summary

The PR adds an optional `n_jobs` parameter to `lance.write_dataset` so a large, fully
in-memory `pyarrow.Table` can be written in parallel instead of as a single sequential
stream. When `n_jobs` is `None` (the default) or `1`, the original sequential write path
is preserved exactly, so existing callers are unaffected. When `n_jobs >= 2` with
`mode="overwrite"`, the table is divided into contiguous, non-empty partitions that are
written concurrently through `lance.fragment.write_fragments` (using a standard-library
`concurrent.futures.ThreadPoolExecutor`), and the resulting fragments are collected in
deterministic partition order and committed through one final `LanceOperation.Overwrite`
transaction.

Unsafe or unsupported combinations are rejected with descriptive errors rather than
silently degraded: non-`pyarrow.Table` inputs, `mode="create"`/`"append"`, invalid worker
counts, and options the parallel path cannot honor. No new dependency is introduced. The
change addresses issue #1980 and closes it via a `Closes #1980` line in the PR body.

### Scope Decision and Phase Consistency

The Phase II implementation plan originally considered broader parallel support across
`create`, `overwrite`, **and** `append`. Phase III and Phase IV intentionally narrowed the
first safe implementation to **parallel `overwrite` only**, because the public
fragment-commit path cannot faithfully preserve:

- the **atomic create-only** guarantee the native writer enforces (it raises if the
  dataset already exists); and
- **append's conflict-detection and retry** semantics (the native append path retries on a
  commit conflict; a blind `Overwrite` with no `read_version` could silently replace a
  concurrently created dataset).

This narrowing was a **deliberate, correctness-driven engineering decision, not an
unfinished or accidental omission**. Shipping `create`/`append` on top of the current
public primitives would have quietly weakened their transaction guarantees. Parallel
`create`/`append` are therefore documented as future work that most likely needs a
Rust-core implementation owning those semantics (and shareable across all bindings). This
keeps Phases I–IV internally consistent: the broad Phase II exploration converged, through
the Phase III engineering review, to the safe overwrite-only scope that Phase IV submitted.

## Learnings and Reflections

### Technical Skills Gained

- **Traced a Python API into a Rust-backed implementation.** Followed
  `lance.write_dataset` through the PyO3 bridge into the Rust dataset and transaction code,
  reading `WriteParams`, `write_fragments`, and the `Operation::Overwrite` commit path
  rather than treating the binding as a black box.
- **Designed a bounded parallel write path.** Partitioned an in-memory table into
  contiguous non-empty slices, drove them through a `ThreadPoolExecutor` that releases the
  GIL during the Rust write, preserved deterministic partition order, and capped effective
  workers at the number of non-empty partitions.
- **Understood fragment metadata and temporary fragment-ID reassignment.** Learned that
  `write_fragments` stamps every returned fragment with a temporary id `0`, and that
  `Operation::Overwrite` reassigns all id-`0` fragments to unique sequential ids at commit
  — the reason concurrent overwrite fan-out is safe even when a partition spills into
  several fragments.
- **Preserved transaction guarantees.** Kept the parallel path all-or-nothing (a single
  final commit; the first worker error re-raised before commit), and deliberately refused
  modes whose guarantees could not be preserved.
- **Wrote failure-path and compatibility tests.** Covered worker failure before commit,
  invalid/`bool`/non-integer worker counts, oversized worker counts, empty tables, null
  columns, unsupported inputs/options, and `None`/`1` sequential parity.
- **Rebased a contribution onto active upstream development.** Verified a conflict-free
  rebase read-only with `git merge-tree`, rebuilt the native extension against the new
  base, and re-ran the full validation suite before submitting.
- **Separated local benchmark evidence from production claims.** Reported medians over
  repeated runs with a warm-up and full-content verification, and framed the local-SSD
  numbers as a mechanism/correctness demonstration, not object-store or production proof.
- **Distinguished automated checks from human maintainer feedback.** Verified PR state with
  read-only `gh` queries and treated CodeRabbit and GitHub Actions output as automated
  signal, never as maintainer review or approval.

### Challenges Overcome

- **A "good first issue" that was simple at the API level but deep at the commit level.**
  Adding a parameter was trivial; making it correct required understanding fragment
  commits and transaction semantics.
- **Discovering that parallel `create`/`append` could introduce correctness races.** A
  blind `Overwrite` with no `read_version` cannot reproduce create-only atomicity or
  append conflict-retry, so those modes could silently lose or replace data under
  concurrency.
- **Reducing the implementation to a safe overwrite-only scope.** Rather than ship weaker
  guarantees, I narrowed the first cut to `mode="overwrite"` and documented the rest as
  future work — a deliberate correctness trade-off, not an omission.
- **Proving concurrent fragments receive safe IDs at the final commit.** The 1000-row
  tests only produce one fragment per partition; I confirmed the multi-fragment-per-
  partition case by reading the Rust id-reassignment logic, not by trusting green tests.
- **Validating behavior after 57 upstream commits landed.** The rebase pulled in new tests
  in the same module (raising the full-suite count from 227 to 236) and touched Rust that
  required a native rebuild before results could be trusted.
- **Reporting modest benchmark gains honestly.** Local SSD showed only a 1.09×–1.17×
  speedup; I reported it as-is with the caveat that the reporter's network-bound scenario
  was not reproduced, instead of overstating the benefit.

### What I Would Do Differently Next Time

- **Ask for maintainer placement guidance earlier.** Raising the Python-vs-Rust-core
  question before implementing would have de-risked the design direction sooner.
- **Identify transaction constraints before implementing all modes.** Mapping the
  create/append semantics up front would have led straight to the overwrite-only scope
  instead of arriving there through a mid-implementation review.
- **Design a dedicated large-table test that forces multiple fragments per partition**, so
  the fragment-ID-reassignment guarantee is exercised by CI rather than only reasoned
  about.
- **Plan the final benchmark methodology earlier** (fixed data, warm-up, repetition count,
  and content verification) so Phase II and Phase IV numbers are directly comparable.
- **Keep phase documentation synchronized with rebases and rewritten commit SHAs**, so
  references never point at an orphaned pre-rebase commit.
